## Context

The engine has three doors by requirement (DOOR-001 to DOOR-003) and must refuse any door-only capability. The sibling library established the hexagonal shape as the shelf's reference implementation, and the platform's test surface (unit, integration, e2e) reads best over a core that imports nothing from its adapters.

## Decision

One core package holds the domain model, the schema validator, the port protocols and the use cases, and imports no adapter, no framework and no driver. The inbound port set is a closed registry of nine names; each door declares which routes or tools adapt which port, and a test holds the three declarations to the registry in both directions. Outbound needs (the session store, the capture store, the renderer, the git home, the clock, the ids) are protocols the adapters satisfy, wired once in a composition root.

## Rationale

- Hexagonality is an import-graph fact, so it is decided by reading the imports rather than reviewing a diagram.
- A closed port registry makes door parity a test over the set rather than a hand-checked list.
- One use case per port is what lets every door validate, refuse and record through the identical path.

## Alternatives considered and rejected

- **A Node backend**: the scaffold, the intent runtime already in CI and the architecture export pin Python, and the exemplar is the Python one.
- **Per-door services**: two implementations of one rule drift exactly where it hurts; the write-door claim exists to forbid it.
