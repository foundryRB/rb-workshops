## Context

The port table pins routes such as `POST /sessions` and `GET /sessions/{id}`. The SPA serves its pages from the same origin, and its session page lives at `/sessions/{id}`; a browser navigation and an API read of one path cannot both be right. The oauth2-proxy sidecar also needs one prefix to treat as machine routes.

## Decision

The API door mounts under `/api`; every route keeps its pinned shape relative to that mount. The SPA's pages own the bare paths. The sidecar's `--api-route=^/api/` makes an unauthenticated API call answer 401 rather than a redirect, and `/api/health` stays open for the platform's probe.

## Rationale

- One origin, two address spaces, no content negotiation.
- The doors page and the doors reference state the mounted routes, so the table is what the door serves.

## Alternatives considered and rejected

- **Content negotiation on the bare paths**: a fragile split of one address by Accept header.
- **Serving the SPA on a different host**: a second hostname for one app.
